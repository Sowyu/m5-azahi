# T6050 secondary CPUs: live results, 2026-10-31

**Status: not fixed.** CPU0 is still the only proven core. No boot image, boot policy,
disk layout or firmware changed. After the tests, one normal `systemctl reboot` returned
to Fedora with Wi-Fi, HTTPS, SSH, the input and power services and a writable root. Normal
power-off was not re-run. Physical keyboard and trackpad use was not re-checked; the logs
show the touch firmware ready.

## What changed in how we can test

- **Reset from the helper works.** `macvdmtool reboot debugusb` restarted the target
  and Fedora returned in about 65 s with no input. This held for seven resets, six of
  them with one or more secondaries left powered on.
- **DebugUSB console works.** `macvdmtool debugusb` needs no reset, and channel 0
  shows iBoot Stage 2 and the full loader log. Linux itself does not print there.
- **Tests run from a Linux module.** No boot image change or proxy session is needed.
  The loader's memory lies outside Linux's RAM fence and is unused after handoff.

Recovery from a CPU0 bus hang or SError is **still unproven**. No test caused one.

## Hardware observations

Kernel 7.0.13-400, system firmware mBoot-20457.41.3, OS firmware mBoot-18000.161.9.
Sources are in [`smp/live`](../smp/live/README.md).

| Test | Result |
| --- | --- |
| CPU1 with Apple's write order | Powered in under 5 us, no entry |
| CPU6, CPU12 | Same |
| CPU1 to CPU5 in one mask | All powered, no entry, same status as a single start |
| CPU6 after a cluster-control cycle | Bit 4 stuck set, bit 5 never set, no entry |

The trap filled every word of the first 1 MiB of the loader image and the 48 KiB sled
with `bl`, so a landing address would have been recorded. No crumb appeared within 2 s.
A fast IPI and SEV after power-on changed nothing, and `L2C_ERR` stayed zero.

Status register `cpu-impl-reg+0x100`:

| State | Value |
| --- | --- |
| Off | `0xCC80_4000_0000_d800` |
| About 10 us after the doorbell | `0xCC80_8000_0000_d800` |
| Powered, cluster 0 | `0xCC80_80ca_ef20_d102` |
| Powered, cluster 1 | `0xCC80_804a_efa0_5102` |
| Powered, cluster 2 | `0xCC80_804a_ef20_5102` |
| Running CPU0 | `0x0080_802a_ef20_1102` |

`CC` is the core number in each nibble, so it carries no state. The `+4` write alone
changes nothing here; the doorbell starts the transition. Bits 39:37 and 15:14 differ
between a released core and running CPU0 and do not change afterwards. That is
consistent with a core stopped before it runs, but the field meanings are inference.
This does not prove where the core is or that it is halted.

One unexplained reading: MCPM1 power read `0x100` once just before the cluster cycle.
Eight later samples and the other snapshots read `0x1f0`.

## Firmware comparison against chips where secondaries work

Public 26A428 restore files, analyzed locally, with nothing executed:

- iBoot for J714s, J813, J616s, J873g and J713 use the same IMPDEF system registers.
  J714s and J813 have none the other lacks.
- iBoot's flow after the reset-vector write has the same shape on J714s and J813.
- SPTM for T6050 and T8142 use identical system register sets. The T6050-only code
  blocks inspected are not CPU bring-up.
- The wake sequence `cluster_ctl=0xf, poll bit 5, cluster_ctl=0x2f, doorbell` exists on
  both T6050 and T8142. It is a wake-path detail, not a T6050-only difference.
- `cpu-impl-reg` is `0x9018` long on T6050 and `0x9010` on T8142, T6040 and T8152. No
  user of the extra register was found.

So no T6050-specific firmware step has been found. That is a limit of this search.

## Outside evidence

Other people's results, not reproduced here:

- Upstream m1n1 [`25b1d89ca50b`](https://github.com/AsahiLinux/m1n1/commit/25b1d89ca50b)
  reports SErrors on M4 for writes to `cpm-impl-reg+0x40f8`. That is the saved ACC lead
  `0xe440f8`. Another M5 Pro project
  ([omarchy-m5](https://github.com/betizzel/omarchy-m5)) reports that reading or writing
  it hangs the bus on T6050. **The ACC lead is closed for raw boot: do not access it.**
- Aurora Silicon reports all cores starting through the same release writes on
  [T8142](https://github.com/aurora-silicon/m1n1/pull/12) and
  [T8152](https://github.com/aurora-silicon/m1n1/pull/14), and their
  [support data](https://github.com/aurora-silicon/aurora-silicon.github.io/blob/main/src/data/support.json)
  lists J714s with 18 working cores.
- Their [T6050 kernel docs](https://github.com/aurora-silicon/linux/blob/t6050/base/Documentation/driver-api/firmware/aurora-apif.rst)
  describe Linux as a guest under their Aura monitor with SPTM active, and
  [Aura's notes](https://github.com/aurora-silicon/aura/blob/main/docs/releases/0.1.0.md)
  keep Mach-O/SPTM work private. Whether SPTM is what makes their T6050 cores start is
  an inference. No public source shows the release path.

## Next steps

1. Ask Aurora's developers how T6050 secondaries are released, and whether a raw boot
   ever worked. This is the cheapest way to save a lot of work.
2. Decode the status register fields with evidence.
3. Assess an SPTM-based boot on paper. It would replace how storage, Wi-Fi and DMA reach
   the hardware, since Aurora's drivers go through SPTM calls, so it is a redesign and
   not a loader patch.

If a core ever enters the loader, Linux still needs the M4+ WFI handling
([PR 672](https://github.com/AsahiLinux/m1n1/pull/672)): `idle=nop arm64.nowfxt`, or a
kernel quirk covering T6050 parts `0x064`/`0x065`. Without it, Aurora reports T8142
secondary idle tasks panic with cleared registers.

Do not repeat the tests above under a new name, and do not write registers because a
firmware table mentions them.
